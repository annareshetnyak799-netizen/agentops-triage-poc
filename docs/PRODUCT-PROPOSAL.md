# Product Proposal — AgentOps Triage PoC

## 1) Идея и прикладная задача
В on-call режиме инженер тратит время на первичный triage инцидента: собрать симптомы (alerts/metrics/logs), найти релевантный runbook, сформировать гипотезы и первые действия. Это повторяющаяся задача с высокой стоимостью ошибки (опасные команды, неверные выводы, утечки данных).

**Идея:** агентная система, которая по инциденту автоматически:
- собирает контекст через инструменты (read-only: метрики/логи),
- достаёт релевантные runbooks из базы знаний,
- ведёт state & memory сессии,
- формирует структурированный план triage (hypotheses + next steps),
- соблюдает safety: PII redaction, tool allowlist, approval на рискованные действия,
- логируется и оценивается через eval harness.

## 2) Для кого и какая боль
**Пользователи**
- SRE/DevOps on-call: быстрее понять “что сломалось” и что делать первым
- Тимлид/платформа: меньше эскалаций и рутины, стандартизация triage
- Бизнес: ниже простой (MTTR) → меньше потерь

**Боль сейчас**
- контекст размазан по источникам (алерты, дашборды, логи, runbooks),
- runbooks сложно найти и применить под текущий контекст,
- ошибки при стрессовой ситуации и высокий риск unsafe действий.

## 3) Цель и метрики успеха
### Продуктовые (эффективность)
- **TTFA p95 ≤ 30s** — время до первого осмысленного плана действий
- **Сокращение времени triage** (proxy): сравнение “человек vs агент” на 10 кейсах

### Агентские (качество)
- **Plan Quality Score (rubric avg)**: ≥ 70% кейсов проходят порог “полезный план”
- **Precision@3 next steps ≥ 0.7**

### Технические (надёжность)
- **Tool success rate ≥ 0.9**
- **Fallback correctness rate ≥ 0.8** (корректная деградация при сбоях tools)

### Safety (must-have)
- **PII leakage rate = 0**
- **Policy violation rate = 0** (нет опасных действий без approval)

## 4) Что именно сделает PoC на демо
На демо показываем 2–3 сценария:
1) “Нормальный” инцидент: алерт → агент дергает metrics/logs → находит runbook → выдаёт план
2) “Tools недоступны”: timeout/403 → агент деградирует в KB-only → спрашивает данные/даёт альтернативы
3) “Injection/PII”: в логах есть инъекция/PII → агент не нарушает policy, PII редактируется

В каждом кейсе демонстрируется:
- шаги агента (plan → tool → observe → decide),
- ссылки на источники (tools/KB refs),
- safety: блокировка опасных действий и PII redaction.

## 5) Что НЕ делает PoC (out-of-scope)
- Автоматическое remediation в проде без человека (no auto-write)
- Полная интеграция с реальными секретами/доступами production
- 100% точный RCA: PoC даёт гипотезы и первые шаги, а не “истину”
- Полный UI: достаточно CLI или минимального HTTP API

## 6) Сценарии использования + edge-cases
### Основные сценарии
- Spike 5xx: определить, это деплой/зависимость/DB; предложить первые проверки
- Latency spike: найти saturated ресурсы; указать, какие метрики/логи смотреть
- Queue backlog: проверить consumer lag, throughput, ошибки обработчиков

### Edge-cases
- tools timeout/5xx → retry → fallback KB-only
- конфликт сигналов (алерт горит, метрики “норм”) → ветвление гипотез + запрос уточнений
- шумные/пустые логи → уточняющие вопросы
- prompt injection в KB/logs → игнорировать, следовать policy
- PII в логах → маскирование до ответа/логирования

## 7) Ограничения (SLO и операционные)
### SLO / performance
- p95 end-to-end latency ≤ 30s
- лимит tool-calls на запрос (например, ≤ 6)
- лимит токенов/стоимости на запрос (конфигом)

### Операционные
- mock/fixtures вместо реальных интеграций на PoC
- запрещены write-инструменты по умолчанию
- прозрачность: агент должен явно говорить, что он “не уверен” и чего не хватает

## 8) Архитектурный набросок (модули и интеграции)
**Компоненты PoC**
- API/CLI вход: `/incident` → новая сессия
- Orchestrator: planner/router + tool executor + state manager
- Tools:
  - MetricsTool (read-only)
  - LogsTool (read-only)
  - KBTool (search runbooks / RAG)
- State & Memory:
  - session store, step history, summaries
- Safety Layer:
  - PII redaction
  - tool policy allowlist
  - approval workflow
- Observability:
  - structured logs + metrics + trace of steps
- Eval Harness:
  - fixtures, rubric, отчет

## 9) Data Flow: что делает агент, а что нет
### Делегируется LLM/Agent
- формирование гипотез и next steps
- выбор инструментов и запросов (в рамках политики)
- суммаризация контекста сессии
- генерация структурированного отчёта

### НЕ делегируется (правила/детерминизм)
- контроль безопасности (PII scrubber, tool policy, approval) — строго не-LLM
- доступы/секреты — не в PoC
- исполнение write-операций — запрещено по умолчанию
